# Documentation Writing Style

## Purpose

Repository documentation should be operationally useful and editorially alive. It should help a reader understand and operate a system while making clear why the system exists, what is at stake, and how its parts connect.

Do not treat all documentation as a sterile technical wiki. Do not force every page into literary prose either. Select the mode that serves the page.

## Page modes

### Orientation and overview

Use an overview page to establish the project’s purpose and point of view. Start with a clear title, an optional one-sentence deck, and concrete prose that helps the reader enter the system before the detail begins.

### Guide and field manual

Use a guide when a reader needs to understand a repeatable practice. Explain the real situation, its decision points, and its consequences before or beside the procedure. A guide should make the work feel legible, not merely ordered.

### Reference and runbook

Use reference pages and runbooks for exact facts, commands, boundaries, and safe operations. Be direct. Add narrative context only where it prevents an error or helps the reader understand why a control exists.

## Voice principles

- Begin with specificity when it helps: an object, machine, file, room, body, or real operating situation can make an abstraction understandable.
- Let technical prose accumulate toward a clear claim. Use short declarative sentences as impact, boundary, or restraint—not as the only cadence.
- Keep the operator visible when their judgment, uncertainty, or responsibility is part of the system’s meaning.
- Use humor sparingly to puncture mechanical absurdity, ceremony, or false certainty. Never let it obscure a safety boundary or diminish a vulnerable person.
- Return to a useful image, phrase, or object only when it gathers new meaning.
- Trust the reader. State the technical conclusion and safety requirements; do not attach a needless moral summary to material that has already shown its human consequence.

## Technical discipline

Lyricism must not blur the difference between observation, test result, inference, plan, and hypothetical behavior. Name evidence boundaries. Preserve exact distinctions between capability, authorization, and impact.

When a system carries risk, explain what was tested, what was not tested, and what controls prevent the next step. A strong narrative does not create false certainty.

## Avoid

- generic thought-leadership or corporate innovation language
- a performed technical-writer voice with no actual point of view
- decorative metaphors that make a procedure less clear
- jokes in place of analysis
- inflated claims about novelty, danger, or maturity
- endings that restate the lesson after the material has already earned it
